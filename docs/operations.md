## Configuration reference

Configuration is read from environment variables by `internal/config/config.go`. A malformed value (not a positive integer or duration) makes the process exit at start with a message naming the variable. Durations use Go syntax (`90s`, `15m`, `24h`). There is no upper bound check beyond what the type can hold.

### How values reach the containers

`compose.yaml` passes only some variables through from the host shell (or an `.env` file next to `compose.yaml`):

- **Shared anchor** (`x-shared-env`, identical for `api` and `worker`, so they cannot diverge): `CONVERTFLOW_JOB_TIMEOUT`, `CONVERTFLOW_RETENTION`, `CONVERTFLOW_STALE_AFTER`, `CONVERTFLOW_MAX_QUEUE_AGE`, `CONVERTFLOW_MAX_ATTEMPTS`, and `CONVERTFLOW_FLAVOR` (fed from `FFMPEG_FLAVOR`). The janitor runs inside the API container and applies the same windows the worker enforces. `tests/container/hardening.sh` fails if the two diverge. **Set these only through the host environment or `.env`, never separately on one service.**
- **API only:** `CONVERTFLOW_MAX_UPLOAD_BYTES` (host-settable), `CONVERTFLOW_SESSIONS` (host-settable, default `off`; the other session and quota variables go into an override file), `CONVERTFLOW_LISTEN` (fixed to `0.0.0.0:8080` in the container; the published host port is `${CONVERTFLOW_PORT:-8080}` on `127.0.0.1`), `CONVERTFLOW_DATABASE_URL_FILE` (fixed to the secret).
- **S3 profile** (`compose.s3.yaml`, development and tests only, see [on-demand.md](on-demand.md)): sets `CONVERTFLOW_STORAGE=s3` and the S3 variables for api and worker with separate key files, and passes `CONVERTFLOW_S3_PUBLIC_ENDPOINT`, `CONVERTFLOW_S3_BUCKET`, `CONVERTFLOW_S3_PRESIGN_TTL`, `CONVERTFLOW_MAX_UPLOAD_BYTES` and `CONVERTFLOW_MAX_OUTPUT_BYTES` through from the host to both.
- **Everything else** is not wired through `compose.yaml`; set it with an override file (see below). `CONVERTFLOW_DATA_DIR` is set to `/data` by both images.

Compose-level variables (not read by the Go code): `CONVERTFLOW_PORT` (host port, default 8080), `CONVERTFLOW_S3_PORT` (host port of the dev/test store of `compose.s3.yaml`, default 9000), `CONVERTFLOW_S3_CORS_ORIGINS` (UI origins that store accepts, default `http://127.0.0.1:${CONVERTFLOW_PORT}`), `CONVERTFLOW_VERSION` (image tag, default `dev`), `FFMPEG_FLAVOR` (`lgpl`|`full`, default `lgpl`), plus `FFMPEG_VERSION`/`FFMPEG_SHA256` from `docker/ffmpeg.env` for builds.

Example override file (`compose.override.yaml` next to `compose.yaml` is picked up automatically; the file below was verified for the TLS case, see below):

```yaml
services:
  api:
    environment:
      CONVERTFLOW_MAX_QUEUED_JOBS: "50"
  worker:
    environment:
      CONVERTFLOW_MAX_DURATION_SEC: "7200"
```

### MAX_QUEUE_AGE: how long a job nobody can run is kept

`CONVERTFLOW_MAX_QUEUE_AGE` only ever fails jobs that **cannot be run** (unless `CONVERTFLOW_WORKERS_ON_DEMAND=true`, see below): the janitor fails a queued job older than this value only if its preset is not runnable by any live worker. A preset is runnable when a **single** live worker (for the janitor: seen within the last 2 minutes, or twice `STALE_AFTER` if that is longer, so a short gap in a worker's registration refreshes does not count) advertises all encoders of one of its candidates, which is exactly the rule that worker's claim query applies. Encoders split across two workers do not count (such an upload is refused with 422 and the preset is not listed by `GET /api/v1/presets`; the API, the upload check and the janitor share one helper, `presets.Runnable`, including the `CONVERTFLOW_FLAVOR` policy). A healthy backlog of a runnable preset is therefore never failed by age, however long it is; it only waits. If the last worker that could run a preset disappears, its queued jobs older than `MAX_QUEUE_AGE` are failed with "no worker available for this preset" at the next janitor pass (once the worker has been silent for that window). Tests: `TestSweepKeepsBacklogOfRunnablePresetAndExpiresUnsupportedOnes`, `TestSweepExpiresPresetOnlySplittableAcrossWorkers`, `TestPresetSplitAcrossWorkersIsRefusedAndNotListed`.

The age is measured from the **last transition into `queued`** (`updated_at`): the upload for a new job, or the requeue of a job whose worker stopped heartbeating (`STALE_AFTER`, up to `MAX_ATTEMPTS` attempts). A requeued job therefore gets a fresh `MAX_QUEUE_AGE` window instead of being failed at once because it was created long ago. Test: `TestExpireQueuedCountsFromLastQueuedTransition`.

**Workers on demand.** When workers scale to zero there is no live worker most of the time, so "no live worker can run it" would fail every job older than `MAX_QUEUE_AGE` while the deployment waits for its autoscaler, and say nothing about whether a worker will come. With `CONVERTFLOW_WORKERS_ON_DEMAND=true` the janitor therefore expires queued jobs **purely by age** ("no worker picked up this job in time"), whatever their preset. Size `MAX_QUEUE_AGE` to the longest backlog your maximum worker count may build up. Tests: `TestSweepOnDemandExpiresByAgeOnly`, `TestSweepOnDemandWithZeroWorkers`, `TestExpireQueuedByAgeIgnoresRunnable`.

## Exposing the service, TLS and reverse proxy

**There is no authentication.** Anyone who can reach the port can submit jobs, download any result, and delete or cancel any job. Treat the network path as the access control and complete [risk-acceptance-template.md](risk-acceptance-template.md) first.

Default: `compose.yaml` publishes `127.0.0.1:${CONVERTFLOW_PORT:-8080}:8080`. To serve a network, change the host IP in the `ports:` line of `compose.yaml` to the intended interface address (compose merges `ports:` lists from override files instead of replacing them, so editing the file is the simplest way), restrict access with the host firewall to the allowed source networks, and put TLS in front.

### DNS rebinding: Host allow-list

A malicious web page can make an operator's browser resolve its own domain name to `127.0.0.1` or a LAN address after the page has loaded; the browser then regards the service as same-origin with that page, and the page can read job lists, filenames and downloads. The browser still sends the attacker's name in the `Host` header, so the API refuses **every** request (all routes: `/api`, SSE streams, downloads, the UI, `/healthz`, `/metrics`) whose `Host` it does not recognise, with `421 Misdirected Request` (problem+json, generic message) and the audit event `request_rejected` with `reason=host_not_allowed` (the offending value is never logged).

- **Default (`CONVERTFLOW_ALLOWED_HOSTS` unset):** `localhost` and any IP literal (IPv4 or `[IPv6]`, with or without a port) are accepted, nothing else. This covers `http://127.0.0.1:8080`, the container `healthcheck` and `curl` against the published port.
- **Using a DNS name, a reverse proxy or an internal service name:** you must list the name, otherwise the service answers `421` (the UI will not load). Set `CONVERTFLOW_ALLOWED_HOSTS=convert.example.org,convert.internal:8443` (comma separated; `host` accepts any port, `host:port` pins the port; hostnames compare case-insensitively; a trailing dot is ignored). Listed names are added to the defaults; they never replace them.
- **Reverse proxy:** forward the client's `Host` unchanged (see below) and list that name, or have the proxy send a `Host` you list.
- **Prometheus and other scrapers** that reach the API by service name (for example `http://api:8080/metrics`) send `Host: api:8080`: add `api` to the list.
- `CONVERTFLOW_ALLOWED_HOSTS=*` turns the check off. Do that only if network access control already makes rebinding irrelevant.

Residual: an attacker who can make the victim's browser use an IP literal that points at the service is not stopped by this check (but also gains nothing, because that is plain cross-origin access, covered by the next section). The check does not protect against non-browser clients. Tests: `TestHostGuardTableAllRoutes` (`internal/api`), `TestRebindingHostRefusedOnEveryRoute` (`internal/e2e`), `internal/hostcheck`.

### Cross-origin requests from browsers

State-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) under `/api/` are refused with `403` (problem+json) when a browser marks them as cross-origin: `Sec-Fetch-Site` present and neither `same-origin` nor `none`, or, without `Sec-Fetch-Site`, an `Origin` header whose host:port differs from the request's `Host` header (scheme is ignored; `Origin: null` is refused). Requests carrying neither header (curl, scripts, automation) are allowed unchanged. The refusal happens before the request body is read, so nothing is stored. Each refusal writes an audit event `request_rejected` with `reason=cross_origin` (no client-supplied strings).

Consequences for operators:

- **A reverse proxy must forward the `Host` header unchanged** (nginx: `proxy_set_header Host $http_host;`). `X-Forwarded-Host` is deliberately not trusted. If the proxy rewrites `Host` (for example to the upstream address), browser uploads from the UI are refused with `403` when the browser sends only `Origin` (plain HTTP to a non-localhost name); non-browser clients are unaffected.
- This does not protect against non-browser clients, or against a page served from the same host:port. Network access control remains the real boundary; see [security.md](security.md).
- `GET` endpoints never change state, so cross-origin reads are not blocked here (the browser's same-origin policy prevents a foreign page from reading the responses; `Cross-Origin-Resource-Policy: same-origin` is also set).

### Option 1: TLS in the application (verified)

Mount the certificate and key read-only and set the two variables (override file, verified with a self-signed certificate; the API answered HTTPS with `Strict-Transport-Security`, its container healthcheck stayed `healthy`, and a TLS 1.1 handshake was refused):

```yaml
services:
  api:
    environment:
      CONVERTFLOW_TLS_CERT_FILE: /run/tls/tls.crt
      CONVERTFLOW_TLS_KEY_FILE: /run/tls/tls.key
    volumes:
      - /srv/convertflow/tls:/run/tls:ro
```

```bash
podman compose -f compose.yaml -f tls.override.yaml up -d --no-build
curl --cacert ca.pem https://convertflow.example:8080/healthz
```

Files must be readable by uid 65532 (the key file permission is a trade-off: mode 0644 inside a directory only root and the service can enter, or a dedicated group). The certificate is loaded at start; restart the `api` container after renewal. Only TLS 1.2 and newer are accepted; cipher suites are Go's defaults.

### Option 2: reverse proxy

Terminate TLS in the organization's proxy and forward to the loopback-published port. Requirements for the proxy (example, *unverified* - no proxy was tested with this stack):

- allow request bodies up to `CONVERTFLOW_MAX_UPLOAD_BYTES` and do not buffer uploads to proxy disk (nginx: `client_max_body_size 8g; proxy_request_buffering off;`),
- long read/send timeouts for uploads and downloads,
- no response buffering for `/api/v1/jobs/*/events` (the server sends `X-Accel-Buffering: no`; nginx honors it),
- preserve `Range` requests for downloads,
- forward the `Host` header unchanged (nginx: `proxy_set_header Host $http_host;`) and list that name in `CONVERTFLOW_ALLOWED_HOSTS` ([DNS rebinding](#dns-rebinding-host-allow-list)); the cross-origin check also compares the browser's `Origin` with `Host` (see [Cross-origin requests from browsers](#cross-origin-requests-from-browsers)),
- do not strip the security headers the application sets (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Cross-Origin-Resource-Policy`). The application emits `Strict-Transport-Security` only when it terminates TLS itself, so add HSTS in the proxy.

**`X-Forwarded-For` and similar headers are not evaluated unless `CONVERTFLOW_TRUSTED_PROXIES` lists the proxy.** With it, requests whose TCP peer is in that list are read as follows: the client address is the first entry of `X-Forwarded-For`, read from the right, that is not itself a trusted proxy (a malformed entry stops the walk, so a client cannot forge its way past a trusted hop; several header lines count as one list); `X-Forwarded-Proto: https` (exactly one value) marks the session cookie `Secure`; in `header` session mode the user header is accepted. Configure the proxy to append to `X-Forwarded-For` (nginx: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`) and to overwrite `X-Forwarded-Proto` and the user header. Audit records then carry `client_ip` next to `remote_ip`. List only the proxy's own addresses; a broad prefix lets anything inside it claim any client address or user. The `remote_ip` in the audit log is always the TCP peer address. Behind a reverse proxy that is the proxy's address, so attribute clients from the proxy's access log, correlated by time. Also with the default rootless-podman published port the peer address is not the client's: a request from `127.0.0.1` was logged as `10.89.1.2` (the container network gateway) in the verified setup. Do not rely on `remote_ip` for attribution without checking what your runtime reports.

### Sessions and quotas

By default (`CONVERTFLOW_SESSIONS=off`) there is no notion of a user: every client lists, downloads and deletes every job, exactly as before. Two opt-in modes give each user their own jobs without accounts:

- **`cookie`**: the first `GET /api/v1/presets` (the page's first request), `GET /api/v1/quota` or job creation without a session creates one: 256 random bits in the cookie `cf_session` (`HttpOnly; SameSite=Strict; Path=/api/`, `Secure` when the API terminates TLS or a trusted proxy sends `X-Forwarded-Proto: https`, `Max-Age` = `CONVERTFLOW_SESSION_TTL`). The database stores only the SHA-256 digest; a cookie value the server did not issue is ignored (no session fixation). Clearing cookies, another browser or a private window means a new, empty session: **the old jobs are not reachable any more** and expire with `CONVERTFLOW_RETENTION`. curl and scripts keep the session with a cookie jar (`-c`/`-b`), see [api.md](api.md#sessions-and-quotas).
- **`header`**: the reverse proxy authenticates users (for example OIDC) and sets `CONVERTFLOW_SESSION_HEADER` (default `X-Forwarded-User`); the API believes it only from `CONVERTFLOW_TRUSTED_PROXIES`. A request without it answers `401` on the job routes and `GET /api/v1/quota`. The proxy must overwrite the header (a client-supplied value that the proxy passes through, or appends to, is a user switch; a second value makes the request `401`). Not verified with a real proxy.

In both modes list, get, events, output (also the presigned download redirect), delete/cancel and `/complete` only match the caller's jobs; another owner's job id answers the same `404` as a missing one. Jobs created while sessions were `off` have no owner and are not visible in a session mode (they expire normally); switching back to `off` shows every job to everyone again. `GET /api/v1/presets`, `/healthz` and `/metrics` need no session; `/metrics` reports only global counts.

**Quotas** (the `QUOTA` variables above, 0 = unlimited) are abuse limits on top of the global caps (`MAX_QUEUED_JOBS`, `MAX_CONCURRENT_UPLOADS`, free space), which still apply first. They are checked before any upload byte is read (multipart, using `Content-Length`) and again when the job row is written, inside one database transaction that holds an advisory lock on the owner and client-address keys, so parallel creates (also on several API replicas) cannot exceed a limit. A multipart upload that passes the first check but loses the second to a parallel request is refused after its bytes arrived, and they are removed. Refusals answer `429` with `Retry-After` (60 s for the active-job and byte limits, the exact remaining time for the hourly limits) and are audited as `upload_rejected` with `reason` `quota <kind>`; a single file larger than the byte quota answers `413`. The hourly counts live in the table `rate_events` (one row per created job or session, kept for an hour), so they are shared by all replicas and survive restarts. Clients read their limits and usage at `GET /api/v1/quota`; the UI shows the refusal and the wait.

Per-address limits (`ACTIVE_JOBS_PER_IP`, `SESSIONS_PER_HOUR_PER_IP`) key IPv4 by address and IPv6 by `/64`, and store only a SHA-256 digest of that (pseudonymous: the IPv4 space can be enumerated). Behind a proxy they need `CONVERTFLOW_TRUSTED_PROXIES`, otherwise every client shares the proxy's budget. Users behind one NAT share them too.

## Scaling and resource sizing

```bash
podman compose up -d --scale worker=2 --no-build
```

Verified: after scaling to two, `convertflow_workers_live` reported 2. Each worker takes one job at a time, needs the `media` volume and the `backend` network (both come from the service definition) and registers its own capabilities. Workers sharing a stack must be built from the same flavor.

Defaults from `compose.yaml` (limits, not measurements; ConvertFlow has not been benchmarked):

| Service | CPU | Memory | pids | Scratch |
|---|---|---|---|---|
| api | 1.0 | 512 MiB | 200 | tmpfs `/tmp` 64 MiB |
| worker | 4.0 | 4 GiB | 512 | tmpfs `/tmp` 2 GiB (RAM-backed, counts against the memory limit) |
| db | 1.0 | 1 GiB | 200 | tmpfs `/tmp` |

Guidance:

- SVT-AV1 at default speed can use all CPU of one job. Start with workers = host cores / 4 and measure; raise `cpus` and `mem_limit` of the worker in a copy of `compose.yaml` for high-resolution inputs.
- The `media` volume must hold, at peak, all inputs waiting in the queue plus outputs kept for `RETENTION`. A single upload may be up to `MAX_UPLOAD_BYTES` and an output up to `MAX_OUTPUT_BYTES`. The API refuses uploads (`507`) when free space drops below `MIN_FREE_BYTES`. Inputs are removed after their job finishes; outputs after retention.
- `MAX_QUEUED_JOBS` x `MAX_UPLOAD_BYTES` bounds the worst case for queued inputs; lower the limits rather than relying on `507`.
- AV1 software encoding is slow; the default `speed` is 6 (biased towards speed).

## Upgrades

1. Obtain and verify the new bundle or images (see [supply-chain.md](supply-chain.md)), and read the release notes.
2. Back up the database ([below](#backup-and-restore)).
3. Load the images (`gunzip -c images.tar.gz | podman load`) and run `CONVERTFLOW_VERSION=<new> FFMPEG_FLAVOR=<flavor> podman compose -f compose.yaml -f compose.airgap.yaml up -d --no-build`.
4. Database migrations run automatically when api and worker start and are idempotent. There is no automated downgrade; restore the dump to go back.
5. Jobs running on a stopped worker are requeued after `STALE_AFTER` (up to `MAX_ATTEMPTS` attempts). Finished results stay available until retention.

### Image digests (connected build side)

`compose.yaml` and the Dockerfiles pin base images by digest. Digests go stale (base images receive security fixes). On a connected machine run:

```bash
CONTAINER_RUNTIME=podman scripts/pin-digests.sh     # resolves current multi-arch index digests; review `git diff`, rebuild, test, commit
CONTAINER_RUNTIME=podman scripts/check-pinned-digests.sh --online    # detects drift (the weekly workflow does this)
```

To bump FFmpeg, follow the GPG-verification procedure in [containers.md](containers.md) and update `docker/ffmpeg.env`. Dependency and OS-package updates require a rebuild and a new release; there is no auto-update inside the running containers (OPS.1.1.3 is an operator process).

## Database role and secrets

`scripts/gen-secrets.sh` creates three files in `./secrets` (directory mode 700, umask 077):

| File | Content | Mounted into |
|---|---|---|
| `db_password` | password of the **bootstrap superuser** `convertflow_admin` | `db` only (`POSTGRES_PASSWORD_FILE`) |
| `db_app_password` | password of the **application role** `convertflow_app` | `db` only (read once by the init script) |
| `database_url` | connection URL for `convertflow_app` (`sslmode=disable`) | `api`, `worker` |

The application never connects as a superuser. On the first start of an **empty** data directory the PostgreSQL image entrypoint runs `docker/db-init/10-app-role.sh` (mounted read-only into `/docker-entrypoint-initdb.d`). It creates `convertflow_app` (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), creates the database `convertflow` owned by that role and revokes access for `PUBLIC`. The script reads the password with psql itself from `/run/secrets/db_app_password`, so it appears in no environment variable, process argument or image layer. The migrations (`internal/db`) run as `convertflow_app`: they take an advisory lock and run DDL in the database that role owns. A compromised api or worker can therefore use the database only as that role (no file access, no other databases, no role management); the bootstrap superuser password is not mounted into them. The superuser still exists inside the `db` container (needed by the image and for administration over the local socket, `podman compose exec db psql -U convertflow_admin -d postgres`). `tests/container/hardening.sh` checks that `rolsuper` is false for the application role, that it owns the database, and that no database password is in a container's environment.

`sslmode=disable` stays: the database is reachable only on the internal `backend` network. Anyone with access to that network segment (for example a process that takes over the worker container) could read database traffic; see [security.md](security.md).

### Upgrading an existing deployment (existing `pgdata` volume)

Init scripts run **only when the data directory is empty**. An existing volume keeps its old setup: the application role does not exist and the app still connects as the old superuser `convertflow`. `scripts/gen-secrets.sh` refuses to touch an old `secrets/` directory (it needs all three files), and with the new `compose.yaml` the `db` healthcheck (`-U convertflow_app`) fails until you migrate. Either start fresh (dump, wipe volume, recreate, restore: see [Backup and restore](#backup-and-restore)), or migrate in place:

1. Back up the database (below). Stop the application: `podman compose stop api worker`.
2. Create the new password and URL, keeping the old `db_password` (it belongs to the old superuser `convertflow`, which stays the bootstrap role of this volume):
   ```bash
   (umask 077; head -c 24 /dev/urandom | base64 | tr -d '/+=\n' > secrets/db_app_password)
   chmod 644 secrets/db_app_password
   printf 'postgres://convertflow_app:%s@db:5432/convertflow?sslmode=disable' "$(cat secrets/db_app_password)" > secrets/database_url
   ```
3. Start only the database with the new `compose.yaml` (`podman compose up -d db`; it mounts `db_app_password`) and run the migration as the old superuser. Save the SQL as `upgrade.sql`:
   ```sql
   \set app_pw `cat /run/secrets/db_app_password`
   CREATE ROLE convertflow_app LOGIN
     NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
     PASSWORD :'app_pw';
   ALTER DATABASE convertflow OWNER TO convertflow_app;
   REVOKE ALL ON DATABASE convertflow FROM PUBLIC;
   GRANT CONNECT ON DATABASE convertflow TO convertflow_app;
   REVOKE ALL ON SCHEMA public FROM PUBLIC;
   ALTER SCHEMA public OWNER TO convertflow_app;
   DO $$
   DECLARE r record;
   BEGIN
     FOR r IN
       SELECT format('ALTER %s %I.%I OWNER TO convertflow_app',
                     CASE c.relkind WHEN 'v' THEN 'VIEW' WHEN 'm' THEN 'MATERIALIZED VIEW' ELSE 'TABLE' END,
                     n.nspname, c.relname) AS stmt
       FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
       WHERE n.nspname = 'public' AND c.relkind IN ('r', 'p', 'v', 'm')
         AND pg_get_userbyid(c.relowner) = 'convertflow'
     LOOP
       EXECUTE r.stmt;
     END LOOP;
   END $$;
   ```
   ```bash
   podman compose exec -T db psql -v ON_ERROR_STOP=1 -U convertflow -d convertflow < upgrade.sql
   ```
4. Start everything (`podman compose up -d --no-build`). Verify: `podman compose exec db psql -U convertflow -d postgres -Atc "select usename from pg_stat_activity where datname='convertflow'"` shows only `convertflow_app` for api/worker sessions, and `\du` lists `convertflow` as the only superuser.

The SQL was run against a database created the old way (superuser `convertflow`, the three application tables created by the migrations); afterwards the application role owned all tables, was not a superuser and could run DDL. The full api/worker stack on a migrated volume was **not** exercised. With the old superuser `convertflow` still present on such a volume, the least-privilege benefit applies to the application's connections only; to drop the old superuser you would have to create a new bootstrap role, which is not covered here.

## Backup and restore

Only the PostgreSQL database matters. It holds job metadata (filenames, options, probe summaries, error messages) and nothing else; media files are ephemeral by design and are deleted after `RETENTION`, so they are not part of any backup concept. Treat the dump as confidential (it contains the filenames users chose) and store it encrypted.

Dump (verified; the output contained the `jobs`, `workers` and `schema_migrations` tables):

```bash
podman compose exec -T db pg_dump -U convertflow_app convertflow > backup.sql
```

Run the restore as `convertflow_app` (over the container-local socket) so that the recreated schema and tables belong to the application role. (On a volume created before the role change use `-U convertflow`; see the upgrade note.) Restore (verified on a throwaway stack with the least-privilege role: after the restore the API was healthy and listed the restored job). Stop the application containers first, recreate the schema, load the dump, start again:

```bash
podman compose stop api worker
podman compose exec -T db psql -v ON_ERROR_STOP=1 -U convertflow_app -d convertflow -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
podman compose exec -T db psql -v ON_ERROR_STOP=1 -q -U convertflow_app -d convertflow < backup.sql
podman compose start api worker
```

Notes: after a restore on a different or wiped `media` volume, restored jobs refer to files that no longer exist: downloads answer `410`, and queued/running jobs cannot be processed (not tested). The janitor removes such records after retention; you can also `DELETE` them. Plan the recovery time with this in mind: the service is stateless apart from the database and the in-retention files. Test the restore regularly; an untested backup is not a backup.

## Deletion, storage and encryption

- Files are removed with a plain `unlink`. There is **no secure wipe**; remnants may remain on the underlying storage until overwritten.
- Deletion happens on `DELETE`, after finishing a job (input), at retention expiry (output and database row), and by an orphan sweep (files without a job, or superseded attempt outputs, once older than 6 h). The janitor runs every minute.
- For stronger sanitization (BSI CON.6), put the `media` volume (and `pgdata`) on an encrypted filesystem such as LUKS and destroy the key to sanitize. Name the volume's host path explicitly in the compose file (bind mount) so you know what to encrypt. Also protect or disable swap and make sure the worker's RAM scratch (`/tmp`, tmpfs) cannot be swapped to unencrypted storage.
- With `s3` storage the same deletions remove bucket objects instead, and the bucket's lifecycle rules ([on-demand.md](on-demand.md#setting-up-a-bucket)) are a backstop. Sanitization of the bucket's storage is the store operator's responsibility (provider-side encryption, key destruction).
- Container logs and the database contain filenames; log rotation is `10m x 3` files per container by default.

## Monitoring

- `GET /healthz` returns `200 ok` if the API can ping the database within 2 s, `503` otherwise. The API container healthcheck runs `/convertflow-api healthcheck` against it (TLS-aware). The worker healthcheck is liveness only.
- `GET /metrics` (Prometheus text format, unauthenticated like everything else, also with sessions on; do not scrape it across untrusted networks). It reports global counts only, nothing per owner or client address:

| Metric | Type | Meaning |
|---|---|---|
| `convertflow_jobs{status="queued\|probing\|running\|done\|failed\|canceled"}` | gauge | jobs currently stored per status |
| `convertflow_workers_live` | gauge | workers seen within the last 30 s |
| `convertflow_sse_streams` | gauge | open progress streams |
| `convertflow_uploads_in_flight` | gauge | uploads being received |

Suggested alerts: `convertflow_workers_live == 0` for 2 minutes; `convertflow_jobs{status="queued"}` growing while `workers_live > 0`; free space on the media volume; container restarts.

## Logging and audit events

All components write structured JSON (one object per line) to stdout/stderr; the compose logging driver is `json-file` with rotation. Forward the container logs to the central log infrastructure (OPS.1.1.5; the stack has none of its own). Audit records have `"audit":true`, an `event` name, the `job_id` (empty if there is none) and, for API events, `remote_ip` (the TCP peer, see the proxy note), `client_ip` (only when a trusted proxy reported a different client address) and, with sessions on, `owner`: the first 8 hex characters of the owner key (a digest; never the cookie token or the proxy user id). File contents are never logged; filenames are not part of audit records.

| Event | Source | Extra fields | Meaning |
|---|---|---|---|
| `job_created` | api | `preset` | upload accepted |
| `upload_rejected` | api | `status`, `reason` | upload refused (limit, bad request, invalid options, no space, ...) |
| `upload_failed` | api | `status`, `class` | server-side failure during upload |
| `job_deleted` | api | | job and files deleted on request |
| `job_cancel_requested` | api | | cancel requested for an active job |
| `session_created` | api | | `cookie` mode: a new session was issued (the record has the new `owner` prefix) |
| `session_refused` | api | `reason` | `cookie` mode: no session was issued on a page load because the per-address limit is reached |
| `request_rejected` | api | `status`, `reason` | refused before any handler: `host_not_allowed` (421), `cross_origin` (403), `no_user_header` (401, `header` mode) |
| `sessions_expired` | api (janitor) | `count` | idle sessions deleted after `CONVERTFLOW_SESSION_TTL` |
| `job_started` | worker | `worker`, `attempt` | worker claimed the job |
| `job_finished` | worker | `worker`, `encoder` | conversion succeeded |
| `job_failed` | worker | `worker`, `error` | conversion failed (sanitized error text) |
| `job_canceled` | worker | `worker` | cancellation took effect |
| `job_lease_lost` | worker | `worker` | job was requeued, canceled or deleted while running; worker aborted quietly |
| `job_released` | worker | `worker`, `reason` | job given back for retry without a terminal write: `shutdown` (worker stopped by a signal) or `storage_unavailable`; the janitor requeues it on its next pass (counts as an attempt) |
| `job_expired` | api (janitor) | | finished job removed by retention |
| `job_queue_expired` | api (janitor) | | queued job failed by `MAX_QUEUE_AGE` |
| `jobs_recovered` | api (janitor) | `requeued`, `failed` | jobs of dead workers requeued or failed |
| `orphan_removed` | api (janitor) | `dir`, `reason` | stray file removed (`no_job`, `job_finished`, `superseded`) |

Other log lines (`level` `INFO`/`WARN`/`ERROR` without `audit`) cover start-up and internal errors; internal error details go there and never to API clients.

Example query: `podman compose logs api | grep '"event":"job_created"'`.

## Time synchronization

Timestamps come from the host clock (containers share it); the database uses the same clock for retention and heartbeats. Run NTP/chrony (or the organization's time service) on the host. A host clock that jumps can cause premature retention, premature stale-job requeue, or delayed cleanup. Log correlation across hosts (proxy, central log server) depends on synchronized clocks (OPS.1.1.5).

## Shutdown behavior

Both `api` and `worker` have `stop_grace_period: 45s`.

- **api (SIGTERM):** stops accepting connections, ends SSE streams, and gives in-flight uploads and downloads up to 30 s to finish; after that it closes the remaining connections and exits 0.
- **worker (SIGTERM/SIGINT):** stops FFmpeg, removes the output of the interrupted attempt and **releases the job at once** (its lease is expired; audit `job_released`, `reason` `shutdown`), so the janitor requeues it on its next pass (at most a minute) instead of after `STALE_AFTER`. The input is kept and the job restarts from the beginning on another or the restarted worker. The attempt counts exactly like a worker crash: after `MAX_ATTEMPTS` interruptions the job fails with "worker lost; attempts exhausted" (raise `MAX_ATTEMPTS` on preemptible nodes). The writes after the run are bounded by `CONVERTFLOW_WORKER_SHUTDOWN_TIMEOUT` (10 s); a shutdown that still hangs is cut 5 s later. A cancel request that reached the worker first is still recorded as `canceled`. An always-on worker exits 0; for ephemeral workers see the exit codes in [on-demand.md](on-demand.md#exit-codes).
- To drain gracefully before maintenance, stop accepting uploads (stop the `api` or block at the proxy), wait until `convertflow_jobs{status="running"}` is 0, then stop the workers.

## Hardware acceleration

The default image does **not** include hardware encoders: FFmpeg is configured with `--disable-autodetect` and without NVENC, QSV or VAAPI, and the compose file passes no devices. The presets list `av1_nvenc`, `av1_qsv` and `av1_vaapi` as the first candidates of `video-av1` and the worker would use them if it found them, but nothing in the shipped build can. The path below is **unverified** and not part of the supported setup:

1. Build a custom worker image with FFmpeg compiled for the hardware (the relevant `--enable-*` flags and driver libraries) by modifying `Dockerfile.worker`.
2. Pass the device (`devices: ["/dev/dri:/dev/dri"]`, and `group_add` for the render group so that uid 65532 can open it) or the vendor runtime to the `worker` service in an override file, and set `CONVERTFLOW_VAAPI_DEVICE` if the device is not `/dev/dri/renderD128`.
3. At start each worker runs a short trial encode per candidate encoder and advertises only those that work (it repeats this at most hourly, and after a job failed inside FFmpeg, at most once a minute; every 15 s it only refreshes its liveness row without starting FFmpeg), so presets fall back to software automatically. Check `GET /api/v1/presets` and the job's `encoder_used`.

Passing a device conflicts with the hardening policy: `tests/container/hardening.sh` fails if any service has `devices`. Document the deviation in your risk assessment and adapt the test deliberately.

## Troubleshooting

**No presets (empty list from `/api/v1/presets`, `422` "preset ... is not available on any running worker").** Workers register capabilities when they start (trial encodes take a few seconds) and refresh every 15 s; a worker counts as live for 30 s after its last registration. Check `podman compose ps`, `podman compose logs worker` and `convertflow_workers_live`. A flavor mismatch hides presets: `FFMPEG_FLAVOR` must be the same when starting api and worker (the shared anchor takes it from the host environment, so always export the same value).

**No presets with workers on demand.** With `CONVERTFLOW_WORKERS_ON_DEMAND=true` the API offers what a worker that registered within the last 7 days could run. A fresh installation has no registration yet: run one worker with `--once --idle-exit=1s` (it registers its encoders, finds no job and exits 0) and keep `CONVERTFLOW_FLAVOR` equal on api and worker. Registrations older than 7 days are deleted by the janitor.

**Jobs fail with "conversion stalled (no progress for N minutes)".** FFmpeg reported no progress (no new `out_time`, frame or output bytes) and used almost no CPU for `CONVERTFLOW_JOB_STALL_TIMEOUT`, typically an encoder that failed to initialise but did not exit, or a hang. The worker log line `ffmpeg stalled; job failed` (level `WARN`, with `job_id`) carries FFmpeg's sanitized stderr tail; the job's `error` field deliberately does not. The worker re-runs its encoder detection after such a failure. An encode that is merely slow keeps a CPU core busy and is not killed; if a legitimate job was killed, raise the timeout or set it to `0` (then only `JOB_TIMEOUT` applies).

**Jobs stay `queued` forever.** Either no live worker can encode that job's preset (workers claim only presets they can encode; the job waits), or all workers are busy. Look at `workers_live`, the worker logs, and the queue length. A queued job with no suitable live worker is failed after `MAX_QUEUE_AGE` (a backlog for a runnable preset is never failed by age) with "no worker available for this preset". With workers on demand, check the autoscaler (KEDA) and the worker pods' exit codes; jobs then fail after `MAX_QUEUE_AGE` with "no worker picked up this job in time".

**Uploads answer `507`.** Free space on the media volume is below `MIN_FREE_BYTES` (default 16 GiB, plus the announced upload size). Free space (lower `RETENTION`, delete jobs), enlarge the volume, or lower `MIN_FREE_BYTES` consciously.

**Uploads answer `503`.** Too many concurrent uploads (`MAX_CONCURRENT_UPLOADS`) or the active-job cap (`MAX_QUEUED_JOBS`) was reached. Clients should honor `Retry-After`. Progress streams answer `503` when `MAX_SSE_STREAMS` is reached.

**Uploads answer `413`.** The file exceeds `MAX_UPLOAD_BYTES`, or a reverse proxy body limit applies first.

**Jobs fail.** The `error` field has a sanitized reason: "input has no video stream"/"no audio stream" (wrong preset for the file), duration/pixel/stream limit exceeded, "worker lost; attempts exhausted" (repeated worker death: look at `podman compose logs worker`, memory limit and OOM kills), run-time limit, output size limit, "conversion stalled" (see above), or an FFmpeg error summary for corrupt input.

**Worker is OOM-killed.** Raise `mem_limit` of the worker (the 2 GiB `/tmp` tmpfs counts against it) or lower `MAX_PIXELS`.

**API unhealthy.** `/healthz` 503 means the database is unreachable or saturated: `podman compose logs db api`.

## Known limits

- No authentication and no user accounts. With `CONVERTFLOW_SESSIONS=off` (default) there is no per-user separation: `GET /api/v1/jobs` lists every job. The `cookie` and `header` modes separate jobs per session or proxy user ([Sessions and quotas](#sessions-and-quotas)); a lost cookie means lost access to its jobs.
- The client IP in audit records is the TCP peer address, plus `client_ip` from `X-Forwarded-For` only when the peer is in `CONVERTFLOW_TRUSTED_PROXIES`.
- A restart of a worker restarts the interrupted conversion from the beginning.
- Plain unlink only; use an encrypted volume for sanitization requirements.
- `MAX_QUEUE_AGE` counts from the last time a job became queued, so a requeued job gets a fresh window (see above).
- Browser requests that are cross-origin are refused on state-changing routes; clients without `Origin`/`Sec-Fetch-Site` are not checked (see [Cross-origin requests from browsers](#cross-origin-requests-from-browsers)).
- Not verified: Docker engine, Windows, macOS, hardware acceleration, reverse-proxy examples, the GitHub workflows.
