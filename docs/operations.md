## Configuration reference

Configuration is read from environment variables by `internal/config/config.go`. A malformed value (not a positive integer or duration) makes the process exit at start with a message naming the variable. Durations use Go syntax (`90s`, `15m`, `24h`). There is no upper bound check beyond what the type can hold.

### How values reach the containers

`compose.yaml` passes only some variables through from the host shell (or an `.env` file next to `compose.yaml`):

- **Shared anchor** (`x-shared-env`, identical for `api` and `worker`, so they cannot diverge): `CONVERTFLOW_JOB_TIMEOUT`, `CONVERTFLOW_RETENTION`, `CONVERTFLOW_STALE_AFTER`, `CONVERTFLOW_MAX_QUEUE_AGE`, `CONVERTFLOW_MAX_ATTEMPTS`, and `CONVERTFLOW_FLAVOR` (fed from `FFMPEG_FLAVOR`). The janitor runs inside the API container and applies the same windows the worker enforces. `tests/container/hardening.sh` fails if the two diverge. **Set these only through the host environment or `.env`, never separately on one service.**
- **API only:** `CONVERTFLOW_MAX_UPLOAD_BYTES` (host-settable), `CONVERTFLOW_LISTEN` (fixed to `0.0.0.0:8080` in the container; the published host port is `${CONVERTFLOW_PORT:-8080}` on `127.0.0.1`), `CONVERTFLOW_DATABASE_URL_FILE` (fixed to the secret).
- **Everything else** is not wired through `compose.yaml`; set it with an override file (see below). `CONVERTFLOW_DATA_DIR` is set to `/data` by both images.

Compose-level variables (not read by the Go code): `CONVERTFLOW_PORT` (host port, default 8080), `CONVERTFLOW_VERSION` (image tag, default `dev`), `FFMPEG_FLAVOR` (`lgpl`|`full`, default `lgpl`), plus `FFMPEG_VERSION`/`FFMPEG_SHA256` from `docker/ffmpeg.env` for builds.

Example override file (`compose.override.yaml` next to `compose.yaml` is picked up automatically; the file below was verified for the TLS case, see below):

```yaml
services:
  api:
    environment:
      CONVERTFLOW_MAX_QUEUED_JOBS: "50"
  worker:
    environment:
      CONVERTFLOW_MAX_DURATION_SEC: "7200"
```

### Variables

"Used by" says which component reads the value. "Range" is what the code accepts; sensible operating ranges are in the meaning column.

| Variable | Default | Used by | Meaning and valid range |
|---|---|---|---|
| `CONVERTFLOW_LISTEN` | `127.0.0.1:8080` | api | Listen address `host:port`. The compose file sets `0.0.0.0:8080` inside the container; exposure is controlled by the published port mapping. |
| `CONVERTFLOW_DATABASE_URL` | none | api, worker | PostgreSQL URL. Either this or `_FILE` is required. Avoid it: the password would sit in the process environment. |
| `CONVERTFLOW_DATABASE_URL_FILE` | none | api, worker | Path to a file containing the URL (compose mounts `secrets/database_url` at `/run/secrets/database_url`). Takes precedence over `CONVERTFLOW_DATABASE_URL`. Generated by `scripts/gen-secrets.sh` with `sslmode=disable` (traffic stays on the internal network). |
| `CONVERTFLOW_DATA_DIR` | `/data` | api, worker | Media root with `in/` and `out/`. Must be the same volume for api and worker. |
| `CONVERTFLOW_FLAVOR` | `lgpl` | api, worker | `lgpl` or `full`; anything else is a start error. The API filters presets by flavor, so it must match the worker image. In compose it comes from `FFMPEG_FLAVOR`. |
| `CONVERTFLOW_TLS_CERT_FILE` | none | api | PEM certificate (chain). Must be set together with the key file, else start error. Enables HTTPS (TLS 1.2 minimum) and the HSTS header. |
| `CONVERTFLOW_TLS_KEY_FILE` | none | api | PEM private key. Must be readable by uid 65532. |
| `CONVERTFLOW_VAAPI_DEVICE` | `/dev/dri/renderD128` | worker | VAAPI render device used only if a VAAPI encoder is present and passes its trial encode. Irrelevant for the default image. |
| `CONVERTFLOW_MAX_UPLOAD_BYTES` | `8589934592` (8 GiB) | api | Largest accepted upload; larger gets `413`. Positive integer. |
| `CONVERTFLOW_MAX_PIXELS` | `35389440` (8192x4320) | worker | Largest video frame area (width x height) accepted after probing; violation fails the job. |
| `CONVERTFLOW_MAX_DURATION_SEC` | `21600` (6 h) | worker | Longest accepted input duration in seconds; violation fails the job. |
| `CONVERTFLOW_MAX_STREAMS` | `16` | worker | Maximum number of streams in the input; violation fails the job. |
| `CONVERTFLOW_MAX_ATTEMPTS` | `3` | api (janitor), shared | A job whose worker disappeared is requeued until it has been tried this many times, then failed with "worker lost; attempts exhausted". |
| `CONVERTFLOW_MAX_OUTPUT_BYTES` | `17179869184` (16 GiB) | worker | FFmpeg stops writing at this size (`-fs`) and the job fails. Keep it well below the free space of the media volume. |
| `CONVERTFLOW_JOB_TIMEOUT` | `4h` | worker, api (janitor), shared | Wall-clock limit for one FFmpeg run. **api and worker must have the same value** (use the shared anchor): the janitor will not clean a running job's files until `JOB_TIMEOUT` plus a 30 minute margin has passed. |
| `CONVERTFLOW_RETENTION` | `24h` | api (janitor), shared | Finished (done/failed/canceled) jobs, their output files and metadata are deleted this long after finishing. |
| `CONVERTFLOW_STALE_AFTER` | `60s` | api (janitor), shared | A probing/running job whose worker heartbeat (every 2 s) is older than this is requeued. Keep it well above the 2 s heartbeat, or healthy jobs are requeued. |
| `CONVERTFLOW_MAX_QUEUE_AGE` | `24h` | api (janitor), shared | A job still `queued` this long after creation is failed with "no worker available for this preset" and its input removed. See the warning below. |
| `CONVERTFLOW_WORKER_POLL` | `2s` | worker | Sleep between claim attempts when the queue is empty. |
| `CONVERTFLOW_MAX_CONCURRENT_UPLOADS` | `4` | api | Simultaneous in-flight upload requests; excess get `503` (`Retry-After: 30`). Each holds one connection and streams to disk. |
| `CONVERTFLOW_MAX_QUEUED_JOBS` | `100` | api | Maximum active jobs (queued + probing + running); excess uploads get `503`. |
| `CONVERTFLOW_MIN_FREE_BYTES` | 2 x `MAX_UPLOAD_BYTES` (16 GiB by default) | api | Free space required on the data volume before an upload is accepted (plus the announced upload size when the client sends `Content-Length`); below it uploads get `507`. Default leaves room for one maximum-size upload and a similarly sized output. |
| `CONVERTFLOW_MAX_SSE_STREAMS` | `64` | api | Simultaneous progress streams; excess get `503`. |

### MAX_QUEUE_AGE: size it to your backlog

`CONVERTFLOW_MAX_QUEUE_AGE` must **exceed the longest queue wait you expect**. The janitor fails every job that is still `queued` and was created longer ago than this, whether or not a suitable worker exists. If your backlog (jobs ahead of a job times their run time, divided by the number of workers) can exceed the value, queued jobs are lost with the message "no worker available for this preset". The default of 24 h equals the retention, which is a reasonable upper bound for most sites; lower it only if you also limit `MAX_QUEUED_JOBS`.

**Known limitation:** the age is measured from `created_at`. A job that was requeued after a worker crash (`STALE_AFTER`, up to `MAX_ATTEMPTS` attempts) and has by then been in the system longer than `MAX_QUEUE_AGE` is failed by the same rule, even though a worker did start it earlier.

## Exposing the service, TLS and reverse proxy

**There is no authentication.** Anyone who can reach the port can submit jobs, download any result, and delete or cancel any job. Treat the network path as the access control and complete [risk-acceptance-template.md](risk-acceptance-template.md) first.

Default: `compose.yaml` publishes `127.0.0.1:${CONVERTFLOW_PORT:-8080}:8080`. To serve a network, change the host IP in the `ports:` line of `compose.yaml` to the intended interface address (compose merges `ports:` lists from override files instead of replacing them, so editing the file is the simplest way), restrict access with the host firewall to the allowed source networks, and put TLS in front.

### Option 1: TLS in the application (verified)

Mount the certificate and key read-only and set the two variables (override file, verified with a self-signed certificate; the API answered HTTPS with `Strict-Transport-Security`, its container healthcheck stayed `healthy`, and a TLS 1.1 handshake was refused):

```yaml
services:
  api:
    environment:
      CONVERTFLOW_TLS_CERT_FILE: /run/tls/tls.crt
      CONVERTFLOW_TLS_KEY_FILE: /run/tls/tls.key
    volumes:
      - /srv/convertflow/tls:/run/tls:ro
```

```bash
podman compose -f compose.yaml -f tls.override.yaml up -d --no-build
curl --cacert ca.pem https://convertflow.example:8080/healthz
```

Files must be readable by uid 65532 (the key file permission is a trade-off: mode 0644 inside a directory only root and the service can enter, or a dedicated group). The certificate is loaded at start; restart the `api` container after renewal. Only TLS 1.2 and newer are accepted; cipher suites are Go's defaults.

### Option 2: reverse proxy

Terminate TLS in the organization's proxy and forward to the loopback-published port. Requirements for the proxy (example, *unverified* - no proxy was tested with this stack):

- allow request bodies up to `CONVERTFLOW_MAX_UPLOAD_BYTES` and do not buffer uploads to proxy disk (nginx: `client_max_body_size 8g; proxy_request_buffering off;`),
- long read/send timeouts for uploads and downloads,
- no response buffering for `/api/v1/jobs/*/events` (the server sends `X-Accel-Buffering: no`; nginx honors it),
- preserve `Range` requests for downloads,
- do not strip the security headers the application sets (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Cross-Origin-Resource-Policy`). The application emits `Strict-Transport-Security` only when it terminates TLS itself, so add HSTS in the proxy.

**`X-Forwarded-For` and similar headers are not trusted or evaluated.** The `remote_ip` in the audit log is the TCP peer address. Behind a reverse proxy that is the proxy's address, so attribute clients from the proxy's access log, correlated by time. Also with the default rootless-podman published port the peer address is not the client's: a request from `127.0.0.1` was logged as `10.89.1.2` (the container network gateway) in the verified setup. Do not rely on `remote_ip` for attribution without checking what your runtime reports.

## Scaling and resource sizing

```bash
podman compose up -d --scale worker=2 --no-build
```

Verified: after scaling to two, `convertflow_workers_live` reported 2. Each worker takes one job at a time, needs the `media` volume and the `backend` network (both come from the service definition) and registers its own capabilities. Workers sharing a stack must be built from the same flavor.

Defaults from `compose.yaml` (limits, not measurements; ConvertFlow has not been benchmarked):

| Service | CPU | Memory | pids | Scratch |
|---|---|---|---|---|
| api | 1.0 | 512 MiB | 200 | tmpfs `/tmp` 64 MiB |
| worker | 4.0 | 4 GiB | 512 | tmpfs `/tmp` 2 GiB (RAM-backed, counts against the memory limit) |
| db | 1.0 | 1 GiB | 200 | tmpfs `/tmp` |

Guidance:

- SVT-AV1 at default speed can use all CPU of one job. Start with workers = host cores / 4 and measure; raise `cpus` and `mem_limit` of the worker in a copy of `compose.yaml` for high-resolution inputs.
- The `media` volume must hold, at peak, all inputs waiting in the queue plus outputs kept for `RETENTION`. A single upload may be up to `MAX_UPLOAD_BYTES` and an output up to `MAX_OUTPUT_BYTES`. The API refuses uploads (`507`) when free space drops below `MIN_FREE_BYTES`. Inputs are removed after their job finishes; outputs after retention.
- `MAX_QUEUED_JOBS` x `MAX_UPLOAD_BYTES` bounds the worst case for queued inputs; lower the limits rather than relying on `507`.
- AV1 software encoding is slow; the default `speed` is 6 (biased towards speed).

## Upgrades

1. Obtain and verify the new bundle or images (see [supply-chain.md](supply-chain.md)), and read the release notes.
2. Back up the database ([below](#backup-and-restore)).
3. Load the images (`gunzip -c images.tar.gz | podman load`) and run `CONVERTFLOW_VERSION=<new> FFMPEG_FLAVOR=<flavor> podman compose -f compose.yaml -f compose.airgap.yaml up -d --no-build`.
4. Database migrations run automatically when api and worker start and are idempotent. There is no automated downgrade; restore the dump to go back.
5. Jobs running on a stopped worker are requeued after `STALE_AFTER` (up to `MAX_ATTEMPTS` attempts). Finished results stay available until retention.

### Image digests (connected build side)

`compose.yaml` and the Dockerfiles pin base images by digest. Digests go stale (base images receive security fixes). On a connected machine run:

```bash
CONTAINER_RUNTIME=podman scripts/pin-digests.sh     # resolves current multi-arch index digests; review `git diff`, rebuild, test, commit
CONTAINER_RUNTIME=podman scripts/check-pinned-digests.sh --online    # detects drift (the weekly workflow does this)
```

To bump FFmpeg, follow the GPG-verification procedure in [containers.md](containers.md) and update `docker/ffmpeg.env`. Dependency and OS-package updates require a rebuild and a new release; there is no auto-update inside the running containers (OPS.1.1.3 is an operator process).

## Backup and restore

Only the PostgreSQL database matters. It holds job metadata (filenames, options, probe summaries, error messages) and nothing else; media files are ephemeral by design and are deleted after `RETENTION`, so they are not part of any backup concept. Treat the dump as confidential (it contains the filenames users chose) and store it encrypted.

Dump (verified; the output contained the `jobs`, `workers` and `schema_migrations` tables):

```bash
podman compose exec -T db pg_dump -U convertflow convertflow > backup.sql
```

Restore (verified on a throwaway stack: after the restore the API was healthy and listed the restored job). Stop the application containers first, recreate the schema, load the dump, start again:

```bash
podman compose stop api worker
podman compose exec -T db psql -v ON_ERROR_STOP=1 -U convertflow -d convertflow -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
podman compose exec -T db psql -v ON_ERROR_STOP=1 -q -U convertflow -d convertflow < backup.sql
podman compose start api worker
```

Notes: after a restore on a different or wiped `media` volume, restored jobs refer to files that no longer exist: downloads answer `410`, and queued/running jobs cannot be processed (not tested). The janitor removes such records after retention; you can also `DELETE` them. Plan the recovery time with this in mind: the service is stateless apart from the database and the in-retention files. Test the restore regularly; an untested backup is not a backup.

## Deletion, storage and encryption

- Files are removed with a plain `unlink`. There is **no secure wipe**; remnants may remain on the underlying storage until overwritten.
- Deletion happens on `DELETE`, after finishing a job (input), at retention expiry (output and database row), and by an orphan sweep (files without a job, or superseded attempt outputs, once older than 6 h). The janitor runs every minute.
- For stronger sanitization (BSI CON.6), put the `media` volume (and `pgdata`) on an encrypted filesystem such as LUKS and destroy the key to sanitize. Name the volume's host path explicitly in the compose file (bind mount) so you know what to encrypt. Also protect or disable swap and make sure the worker's RAM scratch (`/tmp`, tmpfs) cannot be swapped to unencrypted storage.
- Container logs and the database contain filenames; log rotation is `10m x 3` files per container by default.

## Monitoring

- `GET /healthz` returns `200 ok` if the API can ping the database within 2 s, `503` otherwise. The API container healthcheck runs `/convertflow-api healthcheck` against it (TLS-aware). The worker healthcheck is liveness only.
- `GET /metrics` (Prometheus text format, unauthenticated like everything else; do not scrape it across untrusted networks):

| Metric | Type | Meaning |
|---|---|---|
| `convertflow_jobs{status="queued\|probing\|running\|done\|failed\|canceled"}` | gauge | jobs currently stored per status |
| `convertflow_workers_live` | gauge | workers seen within the last 30 s |
| `convertflow_sse_streams` | gauge | open progress streams |
| `convertflow_uploads_in_flight` | gauge | uploads being received |

Suggested alerts: `convertflow_workers_live == 0` for 2 minutes; `convertflow_jobs{status="queued"}` growing while `workers_live > 0`; free space on the media volume; container restarts.

## Logging and audit events

All components write structured JSON (one object per line) to stdout/stderr; the compose logging driver is `json-file` with rotation. Forward the container logs to the central log infrastructure (OPS.1.1.5; the stack has none of its own). Audit records have `"audit":true`, an `event` name, the `job_id` (empty if there is none) and, for API events, `remote_ip` (the TCP peer, see the proxy note). File contents are never logged; filenames are not part of audit records.

| Event | Source | Extra fields | Meaning |
|---|---|---|---|
| `job_created` | api | `preset` | upload accepted |
| `upload_rejected` | api | `status`, `reason` | upload refused (limit, bad request, invalid options, no space, ...) |
| `upload_failed` | api | `status`, `class` | server-side failure during upload |
| `job_deleted` | api | | job and files deleted on request |
| `job_cancel_requested` | api | | cancel requested for an active job |
| `job_started` | worker | `worker`, `attempt` | worker claimed the job |
| `job_finished` | worker | `worker`, `encoder` | conversion succeeded |
| `job_failed` | worker | `worker`, `error` | conversion failed (sanitized error text) |
| `job_canceled` | worker | `worker` | cancellation took effect |
| `job_lease_lost` | worker | `worker` | job was requeued, canceled or deleted while running; worker aborted quietly |
| `job_expired` | api (janitor) | | finished job removed by retention |
| `job_queue_expired` | api (janitor) | | queued job failed by `MAX_QUEUE_AGE` |
| `jobs_recovered` | api (janitor) | `requeued`, `failed` | jobs of dead workers requeued or failed |
| `orphan_removed` | api (janitor) | `dir`, `reason` | stray file removed (`no_job`, `job_finished`, `superseded`) |

Other log lines (`level` `INFO`/`WARN`/`ERROR` without `audit`) cover start-up and internal errors; internal error details go there and never to API clients.

Example query: `podman compose logs api | grep '"event":"job_created"'`.

## Time synchronization

Timestamps come from the host clock (containers share it); the database uses the same clock for retention and heartbeats. Run NTP/chrony (or the organization's time service) on the host. A host clock that jumps can cause premature retention, premature stale-job requeue, or delayed cleanup. Log correlation across hosts (proxy, central log server) depends on synchronized clocks (OPS.1.1.5).

## Shutdown behavior

Both `api` and `worker` have `stop_grace_period: 45s`.

- **api (SIGTERM):** stops accepting connections, ends SSE streams, and gives in-flight uploads and downloads up to 30 s to finish; after that it closes the remaining connections and exits 0.
- **worker (SIGTERM):** stops FFmpeg and leaves the job and its input in place; the job is requeued by the janitor after `STALE_AFTER` (counts as an attempt) and restarts from the beginning on another or the restarted worker. Output of the interrupted attempt is removed.
- To drain gracefully before maintenance, stop accepting uploads (stop the `api` or block at the proxy), wait until `convertflow_jobs{status="running"}` is 0, then stop the workers.

## Hardware acceleration

The default image does **not** include hardware encoders: FFmpeg is configured with `--disable-autodetect` and without NVENC, QSV or VAAPI, and the compose file passes no devices. The presets list `av1_nvenc`, `av1_qsv` and `av1_vaapi` as the first candidates of `video-av1` and the worker would use them if it found them, but nothing in the shipped build can. The path below is **unverified** and not part of the supported setup:

1. Build a custom worker image with FFmpeg compiled for the hardware (the relevant `--enable-*` flags and driver libraries) by modifying `Dockerfile.worker`.
2. Pass the device (`devices: ["/dev/dri:/dev/dri"]`, and `group_add` for the render group so that uid 65532 can open it) or the vendor runtime to the `worker` service in an override file, and set `CONVERTFLOW_VAAPI_DEVICE` if the device is not `/dev/dri/renderD128`.
3. At start each worker runs a short trial encode per candidate encoder and advertises only those that work, so presets fall back to software automatically. Check `GET /api/v1/presets` and the job's `encoder_used`.

Passing a device conflicts with the hardening policy: `tests/container/hardening.sh` fails if any service has `devices`. Document the deviation in your risk assessment and adapt the test deliberately.

## Troubleshooting

**No presets (empty list from `/api/v1/presets`, `422` "preset ... is not available on any running worker").** Workers register capabilities when they start (trial encodes take a few seconds) and refresh every 15 s; a worker counts as live for 30 s after its last registration. Check `podman compose ps`, `podman compose logs worker` and `convertflow_workers_live`. A flavor mismatch hides presets: `FFMPEG_FLAVOR` must be the same when starting api and worker (the shared anchor takes it from the host environment, so always export the same value).

**Jobs stay `queued` forever.** Either no live worker can encode that job's preset (workers claim only presets they can encode; the job waits), or all workers are busy. Look at `workers_live`, the worker logs, and the queue length. A queued job with no suitable worker is failed after `MAX_QUEUE_AGE` with "no worker available for this preset".

**Uploads answer `507`.** Free space on the media volume is below `MIN_FREE_BYTES` (default 16 GiB, plus the announced upload size). Free space (lower `RETENTION`, delete jobs), enlarge the volume, or lower `MIN_FREE_BYTES` consciously.

**Uploads answer `503`.** Too many concurrent uploads (`MAX_CONCURRENT_UPLOADS`) or the active-job cap (`MAX_QUEUED_JOBS`) was reached. Clients should honor `Retry-After`. Progress streams answer `503` when `MAX_SSE_STREAMS` is reached.

**Uploads answer `413`.** The file exceeds `MAX_UPLOAD_BYTES`, or a reverse proxy body limit applies first.

**Jobs fail.** The `error` field has a sanitized reason: "input has no video stream"/"no audio stream" (wrong preset for the file), duration/pixel/stream limit exceeded, "worker lost; attempts exhausted" (repeated worker death: look at `podman compose logs worker`, memory limit and OOM kills), run-time limit, output size limit, or an FFmpeg error summary for corrupt input.

**Worker is OOM-killed.** Raise `mem_limit` of the worker (the 2 GiB `/tmp` tmpfs counts against it) or lower `MAX_PIXELS`.

**API unhealthy.** `/healthz` 503 means the database is unreachable or saturated: `podman compose logs db api`.

## Known limits

- No authentication, no users, no per-user separation. Job ids are random UUIDs, but `GET /api/v1/jobs` lists every job.
- The client IP in audit records is the TCP peer address only.
- A restart of a worker restarts the interrupted conversion from the beginning.
- Plain unlink only; use an encrypted volume for sanitization requirements.
- `MAX_QUEUE_AGE` can fail requeued jobs older than the age (see above).
- Not verified: Docker engine, Windows, macOS, hardware acceleration, reverse-proxy examples, the GitHub workflows.
